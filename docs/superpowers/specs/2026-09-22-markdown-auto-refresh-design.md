# Markdown Reader 自动刷新设计

## 目标

已打开的 Markdown Reader 预览必须在源文件内容变化后自动重新渲染。VS Code 内的文本编辑和由 Codex、终端或其他进程造成的磁盘写入都应得到支持；前者是首要路径。

## 方案

`MarkdownEditorProvider` 保留一个以文档 URI 为键的 `DocumentSession`。每个会话维护当前 `TextDocument` 的文本提供器，并向所有已连接的 Webview 广播渲染结果。

刷新有两条入口：

1. `workspace.onDidChangeTextDocument` 是主入口。事件 URI 对应某个预览会话时，提供器先将该会话绑定到事件中的最新 `TextDocument`，再安排重新渲染。
2. 每个有预览面板的文件建立一个精确匹配该文件的 `FileSystemWatcher`。监听到磁盘变更后，提供器重新获取该 URI 的 `TextDocument`、更新会话文本提供器，并安排重新渲染。这条路径覆盖 VS Code 文本模型事件之外的外部写入。

两条入口共用 `DocumentSession.schedule()` 的 200ms 防抖。同一次保存若同时触发两个事件，只会造成一次最终渲染。渲染版本号继续确保较慢的旧渲染结果不会覆盖新结果。

## 生命周期

`DocumentSession` 不再永久捕获第一次打开时的 `TextDocument`。它允许提供器更新文本提供器，因此 URI 对应的文档模型重新创建后，渲染仍读取当前文本。

最后一个关联 Webview 被释放时，提供器会释放该 URI 的文件监听、销毁会话并从映射中移除。重新打开文件必然创建干净会话，不会复用已关闭文档的内容。

## 错误处理与边界

外部监听触发时若 VS Code 无法重新打开文档（例如文件刚被删除或短暂不可访问），本次刷新静默跳过；下一次有效文档或文件事件可继续刷新。删除不显示过期内容之外的额外 UI。已有 `onDidChangeTextDocument` 路径仍负责 VS Code 已加载文档的正常更新。

## 验收与测试

- 文本模型变更应在防抖后把最新 Markdown 发往预览。
- 文件系统变更应重新读取当前文档并刷新预览。
- 两类事件连续到达时只产生一次最终渲染。
- 关闭最后一个预览后，会话和文件监听被释放；随后重新打开并修改同 URI 文件仍能刷新。
- 既有首次渲染、多面板广播和旧渲染丢弃行为保持不变。
